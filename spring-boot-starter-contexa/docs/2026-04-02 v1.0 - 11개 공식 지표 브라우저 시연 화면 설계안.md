# 2026-04-02 v1.0 - 11개 공식 지표 브라우저 시연 화면 설계안

## 1. 목적

이 문서는 `spring-boot-starter-contexa` 모듈 안에서, 현재 TDD 기반으로 검증하던 **11개 공식 컨텍스트 지표**를 **외부 웹브라우저에서 직접 실행하고 실시간으로 검증하는 시연 화면**으로 옮기기 위한 설계안이다.

이번 시연의 목적은 단순히 “점수 95% 이상”을 보여 주는 것이 아니다.  
심사위원이 직접 다음을 눈으로 확인할 수 있어야 한다.

1. 어떤 요청이 실제로 들어왔는가
2. 서버 안에서 어떤 정보가 실제로 수집되었는가
3. 그 정보가 어떤 순서로 이어졌는가
4. 회차가 쌓일수록 어떤 정보가 유지되고 어떤 정보가 늘어났는가
5. 다른 사용자 정보가 섞이지 않았는가
6. 최종 지표 점수가 **임의 계산값이 아니라 실제 수집된 사실**을 바탕으로 계산되었는가

이번 범위는 **11개 컨텍스트 검증 지표 화면**이다.

- `EIR`
- `CCR`
- `CCSR`
- `PFR`
- `MTR`
- `CoR`
- `RAP`
- `RPI`
- `BMA`
- `USNS`
- `BSR`

`CDC / ERA / SUHR`는 별도 LLM 판정 화면에서 다룬다.

## 2. 가장 중요한 원칙

### 2.1 브라우저가 진실값이다

내부 replay, 저장된 JSON, 배치 보고서는 참고 자료일 뿐이다.  
**심사위원이 브라우저에서 본 값이 진실값**이다.

따라서 화면은 다음을 기준으로 설계한다.

- 브라우저에서 누른 버튼이 실제 요청을 발생시킨다
- 서버가 그 요청에서 실제로 모은 원본 정보를 화면에 다시 보여 준다
- 지표 점수는 그 원본 정보를 바탕으로 서버에서 다시 계산한다
- 화면에는 “원본 사실”과 “지표 계산 결과”를 분리해서 보여 준다

### 2.2 더미 데이터 금지

화면에서 보여 주는 값은 아래 3종만 허용한다.

1. 실제 요청에서 수집된 원본 값
2. 원본 값에서 직접 계산된 파생 값
3. 계산식이 공개된 지표 점수

허용하지 않는 것:

- 화면 전용 임의 문구
- 시연용 고정 점수
- 숨겨진 보정값
- 설명을 위한 가짜 이벤트

### 2.3 어려운 용어 금지

UI에는 기술 용어를 그대로 올리지 않는다.

예:

- `event metadata` → `서버가 바로 기록한 값`
- `prompt telemetry` → `AI에 전달된 구성 정보`
- `retrieval audit` → `검색 후보 기록`
- `authorization precision` → `허용 문서만 남았는지`
- `context contamination` → `남의 정보가 섞였는지`

영문 코드(`EIR`, `CCR`)는 유지하되, 항상 쉬운 한국어 설명과 함께 쓴다.

## 3. 현재 재사용 가능한 것과 부족한 것

## 3.1 현재 바로 재사용 가능한 것

현재 `spring-boot-starter-contexa`에는 이미 시연용 뼈대가 있다.

- 현재 테스트 페이지: [security-test.html](/D:/contexa/spring-boot-starter-contexa/src/main/resources/templates/test/security-test.html)
- 현재 테스트 스크립트: [security-test.js](/D:/contexa/spring-boot-starter-contexa/src/main/resources/static/js/security-test.js)
- 현재 evidence 수집 서비스: [SecurityTestEvidenceService.java](/D:/contexa/spring-boot-starter-contexa/src/main/java/io/contexa/springbootstartercontexa/service/SecurityTestEvidenceService.java)
- 현재 evidence API: [SecurityTestEvidenceController.java](/D:/contexa/spring-boot-starter-contexa/src/main/java/io/contexa/springbootstartercontexa/web/SecurityTestEvidenceController.java)
- 현재 SSE 이벤트 발행: [LlmAnalysisEventPublisher.java](/D:/contexa/spring-boot-starter-contexa/src/main/java/io/contexa/springbootstartercontexa/event/LlmAnalysisEventPublisher.java)
- 현재 페이지 진입 경로: [TestPageController.java](/D:/contexa/spring-boot-starter-contexa/src/main/java/io/contexa/springbootstartercontexa/web/TestPageController.java)

현재 화면이 이미 보여 줄 수 있는 것:

- 요청 ID
- 사용자/세션/시나리오
- 즉시 응답
- SSE 타임라인
- evidence JSON
- 서버 기록
- context / outbox / prompt telemetry 일부

## 3.2 현재 부족한 것

지금 화면은 “한 요청의 evidence 확인”에는 유용하지만, **11개 공식 지표를 심사위원이 이해하기 쉽게 입증하는 화면**으로는 부족하다.

부족한 점:

1. 지표별 전용 화면이 없다
2. 회차 누적과 라운드 비교 화면이 약하다
3. “원본 사실”과 “점수 계산”이 분리되어 보이지 않는다
4. 오염 여부, 허용 여부, 누적 여부를 한눈에 보여 주는 그래프가 없다
5. `SandboxPromptBenchmarkMetricExtractor`의 계산식이 브라우저용으로 노출되지 않는다
6. prompt snapshot / retrieval audit / trace lineage를 실시간으로 화면에 묶어 보여 주는 런타임 캡처 계층이 없다

## 4. 브라우저 시연용 전체 정보 구조

화면은 **2단 구조**로 간다.

### 4.1 1차 화면: 11개 지표 전체 현황판

경로 제안:

- `/admin/test/metrics`

역할:

- 11개 지표를 한눈에 보여 주는 입구 화면
- 현재 실행 상태
- 준비 실행 상태
- 최근 점수
- 통과/실패
- 각 지표 상세 화면 이동

핵심 구성:

1. 상단 요약
   - 현재 사용자
   - 현재 세션
   - 현재 실행 ID
   - 준비 데이터 상태
   - 전체 통과 개수

2. 지표 카드 11개
   - 지표 코드
   - 쉬운 한국어 이름
   - 현재 점수
   - 기준값
   - 상태
   - 상세 보기 버튼

3. 그룹 구분
   - 1그룹: 요청과 기록이 정확한가
   - 2그룹: 검색과 누적이 정확한가
   - 3그룹: 사용자 행동 문맥이 살아 있는가

### 4.2 2차 화면: 지표별 상세 화면

경로 제안:

- `/admin/test/metrics/eir`
- `/admin/test/metrics/ccr`
- ...
- `/admin/test/metrics/bsr`

역할:

- 해당 지표 하나만 깊게 검증
- 원본 사실, 계산식, 결과를 같은 화면에서 동시에 확인

각 지표 상세 화면은 같은 틀을 공유한다.

1. 실행 패널
2. 원본 사실 패널
3. 계산 규칙 패널
4. 실시간 변화 패널
5. 최종 점수 패널
6. 다운로드/증적 패널

## 5. 공통 화면 틀

각 지표 상세 화면은 아래 6개 구역을 고정으로 사용한다.

## 5.1 구역 A: 실행 제어

표시 이름:

- `실행 준비`
- `실행하기`

구성:

- 시나리오 선택
- 대상 자원 선택
- 실행 방식 선택
  - `1회 실행`
  - `3회 실행`
  - `공식 검증 실행`
- 준비 실행 버튼
  - 여러 회차가 필요한 지표는 먼저 준비 실행이 필요함
- 본 실행 버튼
- 중지 버튼
- 실행 진행률 바

중요 원칙:

- `준비 실행`도 실제 요청을 발생시킨다
- 어떤 사용자, 어떤 IP, 어떤 UA, 어떤 경로로 준비했는지를 모두 화면에 남긴다
- “몰래 미리 넣어둔 데이터”처럼 보이면 안 된다

## 5.2 구역 B: 지금 막 수집된 원본 사실

표시 이름:

- `서버가 실제로 기록한 값`

구성:

- 요청 기본 정보 표
- 세션 정보 표
- 사용자/권한 정보 표
- 프롬프트 구성 정보 표
- 검색 후보 정보 표
- 전달 기록 정보 표

규칙:

- 이 구역에는 **점수나 해석을 넣지 않는다**
- 오직 원본 사실만 보여 준다

## 5.3 구역 C: 단계별 흐름

표시 이름:

- `어떻게 처리되었는지`

형태:

- 가로 흐름 다이어그램

예:

`브라우저 요청 → 서버 기록 → 세션/행동 수집 → 검색 후보 생성 → 허용 문서 확정 → 프롬프트 생성 → 외부 전달 기록`

각 단계 클릭 시:

- 단계 시작 시각
- 단계 종료 시각
- 그 단계의 원본 JSON
- 관련 requestId / correlationId

## 5.4 구역 D: 회차 변화

표시 이름:

- `회차별 변화`

형태:

- 라인 차트
- 누적 막대
- 회차 표

예:

- 1차, 2차, 3차
- 또는 공식 검증 24회

보여 줄 것:

- 어떤 값이 유지되었는지
- 어떤 값이 새로 생겼는지
- 어떤 값이 줄거나 사라졌는지

## 5.5 구역 E: 계산 규칙

표시 이름:

- `이 점수는 이렇게 계산됩니다`

구성:

- 분자/분모
- 체크 항목
- 각 항목 pass/fail
- 최종 점수

중요:

- 지표는 계산식이 보이지 않으면 신뢰를 얻기 어렵다
- “왜 100점인지”를 화면이 스스로 설명해야 한다

## 5.6 구역 F: 최종 판정

표시 이름:

- `최종 결과`

구성:

- 현재 점수
- 기준 점수
- 통과/실패
- 핵심 이유 3줄
- 증적 다운로드

## 6. 11개 지표를 비전문가용 한국어로 다시 이름 붙이기

화면에서는 코드와 쉬운 이름을 같이 쓴다.

| 코드 | 화면 이름 | 화면 설명 |
|---|---|---|
| `EIR` | 요청 기록 정확도 | 브라우저 요청이 서버 기록과 정확히 맞는지 |
| `CCR` | 문맥 채워짐 정도 | AI 판단에 필요한 정보가 빠짐없이 모였는지 |
| `CCSR` | 문맥 앞뒤 일치도 | 같은 사실이 서로 다르게 기록되지 않았는지 |
| `PFR` | 프롬프트 구성 정확도 | AI에 보낸 내용이 계약대로 만들어졌는지 |
| `MTR` | 추적 연결 정확도 | 요청부터 프롬프트까지 ID와 해시가 끊기지 않았는지 |
| `CoR` | 정보 섞임 방지 | 남의 정보나 잘못된 정보가 섞이지 않았는지 |
| `RAP` | 허용 문서만 남기기 | 검색된 문서 중 허용된 것만 최종에 남았는지 |
| `RPI` | 회차 누적 안정성 | 회차가 늘수록 필요한 기억이 정상적으로 쌓이는지 |
| `BMA` | 기준선 성장 정확도 | 사용자 기준선이 자연스럽게 자라나는지 |
| `USNS` | 개인별 낯섦 감지 | “이 사람 기준”으로 평소와 다른 점을 잡아내는지 |
| `BSR` | 행동 이야기 설명력 | 이상 행동의 흐름과 이유를 설명할 수 있는지 |

## 7. 지표별 상세 화면 설계

## 7.1 EIR - 요청 기록 정확도

### 이 화면이 답해야 하는 질문

- 브라우저에서 보낸 요청과 서버가 기록한 요청이 정말 같은가

### 원본 사실

- 브라우저 요청 헤더
- `requestId`
- `requestPath`
- `clientIp`
- `userAgent`
- `mfaVerified`
- `resourceSensitivity`
- `isSensitiveResource`
- `authMethod`
- `authorizationEffect`
- `effectiveRoles`
- `effectivePermissions`

### 데이터 출처

- [SecurityTestEvidenceService.java](/D:/contexa/spring-boot-starter-contexa/src/main/java/io/contexa/springbootstartercontexa/service/SecurityTestEvidenceService.java)
- request trace
- response trace
- analysis data
- SSE event metadata

### 시각화

1. `브라우저 값 vs 서버 값` 2열 비교표
2. 일치 항목 수 원형 차트
3. mismatch가 있을 경우 빨간 강조

### 판정 방식

- 10개 핵심 항목 중 몇 개가 정확히 맞는지
- 계산식은 현재 TDD와 동일

## 7.2 CCR - 문맥 채워짐 정도

### 이 화면이 답해야 하는 질문

- AI가 판단하는 데 필요한 최소 정보가 모두 들어왔는가

### 원본 사실

- event의 인증/권한/민감도 정보
- session의 사용자/인증/요청 수
- behavior의 OS/브라우저
- prompt execution metadata 존재 여부

### 시각화

1. `채워짐 체크리스트` 12칸
2. `채워짐 비율` 막대
3. 어떤 칸이 비었는지 설명 카드

## 7.3 CCSR - 문맥 앞뒤 일치도

### 이 화면이 답해야 하는 질문

- 같은 사실이 event, prompt, response에 똑같이 나타나는가

### 원본 사실

- requestPath
- clientIp
- mfaVerified
- resourceSensitivity
- authorizationEffect
- demoPhase

### 시각화

1. `사실별 일치 매트릭스`
2. 같은 값을 연결하는 선
3. 모순이 생기면 해당 줄만 빨간색

## 7.4 PFR - 프롬프트 구성 정확도

### 이 화면이 답해야 하는 질문

- AI에 보낸 프롬프트가 계약대로 만들어졌는가

### 원본 사실

- system prompt
- user prompt
- promptSectionSet
- omittedSections
- promptHash
- systemPromptHash
- userPromptHash
- 길이 정보

### 시각화

1. 프롬프트 구성도
2. 포함 섹션 / 빠진 섹션 표
3. 해시/길이 일치 표
4. 원문 보기 / 요약 보기 탭

## 7.5 MTR - 추적 연결 정확도

### 이 화면이 답해야 하는 질문

- 요청부터 프롬프트까지 추적 줄이 끊기지 않았는가

### 원본 사실

- requestId
- correlationId
- promptVersion
- promptHash
- sectionSet
- omittedSections
- promptKey
- templateKey

### 시각화

1. `연결선 다이어그램`
   - 요청
   - 이벤트
   - 프롬프트
   - 전달 기록
2. 각 단계 ID 표시
3. 끊긴 연결은 빨간색

## 7.6 CoR - 정보 섞임 방지

### 이 화면이 답해야 하는 질문

- 검색 후보에 남의 문서나 목적이 다른 문서가 섞였는가

### 원본 사실

- raw retrieved documents
- document userId
- retrievalPurpose
- expected userId
- expected purpose

### 시각화

1. 후보 문서 표
   - 문서 ID
   - 사용자
   - 목적
   - 허용 여부
   - 오염 여부
2. `오염 없음 / 오염 있음` 누적 막대
3. `남의 정보 0건` 강조 배지

### 추가 요구

- 이 지표는 반드시 **다른 사용자 준비 실행**을 선행해야 한다
- 준비 실행 패널에서
  - 타 사용자 A 적재
  - 타 사용자 B 적재
  - 동일 사용자 다른 목적 문서 적재
  를 눈으로 보게 해야 한다

## 7.7 RAP - 허용 문서만 남기기

### 이 화면이 답해야 하는 질문

- 검색된 문서 중에서 허용된 것만 최종에 남았는가

### 원본 사실

- rawRetrievedCount
- authorizeRequestedCount
- authorizeAllowedCount
- authorizeDeniedCount
- deniedReasons

### 시각화

1. 깔때기 그래프
   - 검색됨
   - 허용 검사 대상
   - 허용됨
   - 제외됨
2. 제외 이유 표
3. 최종 포함 문서 표

## 7.8 RPI - 회차 누적 안정성

### 이 화면이 답해야 하는 질문

- 회차가 쌓일수록 관련 정보가 자연스럽게 누적되는가

### 원본 사실

- relatedDocuments count
- previous count
- observation count
- baseline context present

### 시각화

1. 회차별 선 그래프
   - 관련 문서 수
   - 관측 수
2. 회차 표
   - 이전보다 늘었는지
   - 기대 최소치를 만족하는지
3. 역행 시 경고 배지

## 7.9 BMA - 기준선 성장 정확도

### 이 화면이 답해야 하는 질문

- 개인 기준선이 “없음 → 임시 → 쌓임”으로 자연스럽게 자라는가

### 원본 사실

- initial baseline state
- observed work pattern presence
- workProfileSummary
- observation count

### 시각화

1. 3단계 성장 스텝바
   - 아직 없음
   - 임시
   - 쌓임
2. 관측 수 라인 차트
3. 회차별 기준선 상태 표

## 7.10 USNS - 개인별 낯섦 감지

### 이 화면이 답해야 하는 질문

- “누구에게나 낯선가”가 아니라 “이 사람에게 낯선가”를 보여 주는가

### 원본 사실

- current path
- previous path
- observed work pattern
- related documents
- anomaly signal
- signal-specific evidence

### 시각화

1. `평소와 다른 정도` 점 그래프
2. 이전 경로 vs 현재 경로 비교 카드
3. “왜 평소와 다른지” 근거 카드
4. 회차별 히트맵

## 7.11 BSR - 행동 이야기 설명력

### 이 화면이 답해야 하는 질문

- 이상 행동을 단일 점이 아니라 흐름으로 설명할 수 있는가

### 원본 사실

- session narrative
- previous path
- anomaly signal
- surprise context
- recovery support

### 시각화

1. `이전 → 현재 → 다음` 흐름 다이어그램
2. 세션 이야기 카드
3. 회복 여부 표시
4. 근거별 색상 태그

## 8. 준비 실행과 본 실행을 분리해야 하는 이유

11개 지표 중 일부는 단일 요청만으로 입증되지 않는다.

예:

- `CoR`
- `RAP`
- `RPI`
- `BMA`
- `USNS`
- `BSR`

이 지표는 **이전 기록, 다른 사용자 기록, 누적 기록**이 필요하다.

따라서 브라우저 화면에는 아래 두 단계를 명시적으로 둔다.

### 8.1 준비 실행

표시 이름:

- `검증용 기록 쌓기`

특징:

- 실제 요청 발생
- 어떤 계정이 몇 번 실행되었는지 모두 공개
- 준비 데이터가 언제 어떻게 쌓였는지 타임라인으로 표시

### 8.2 본 실행

표시 이름:

- `지금 검증하기`

특징:

- 준비 실행으로 쌓인 실제 기록을 바탕으로 현재 요청을 검증
- 현재 요청이 어떤 기록과 비교되는지 즉시 보여 줌

## 9. 서버-브라우저 데이터 흐름 설계

## 9.1 공통 흐름

```text
브라우저 버튼 클릭
→ 실제 보호 API 호출
→ 요청 등록
→ SSE 이벤트 수신
→ evidence 수집
→ 런타임 캡처 저장
→ 지표 계산
→ 화면 갱신
```

## 9.2 반드시 추가해야 할 런타임 캡처 계층

현재 `SecurityTestEvidenceService`는 요청/응답/evidence를 잘 묶어 준다.  
하지만 11개 지표를 위해서는 아래 런타임 캡처가 추가로 필요하다.

### 추가 서비스 제안

- `MetricDemoCaptureService`
- `MetricDemoPromptTraceStore`
- `MetricDemoRetrievalAuditStore`
- `MetricDemoTraceLineageStore`
- `MetricDemoMetricService`
- `MetricDemoRunService`

### 추가해야 할 원본 캡처

1. 최종 event snapshot
2. sessionCtx / behaviorCtx snapshot
3. prompt raw/system/user snapshot
4. prompt execution metadata
5. retrieval audit raw candidates
6. authorization filtering 결과
7. round progression snapshot
8. baseline maturity snapshot

중요:

- 이 캡처는 테스트 코드의 `sandbox` store를 그대로 끌어오는 방식보다,
- **운영 시연용 런타임 캡처 서비스**로 새로 정리하는 것이 낫다
- 이유는 브라우저 시연에서는 “테스트 전용 보조 코드”보다 “실행 중 실제 서버 기록”처럼 보여야 하기 때문이다

## 11. 심사위원이 “조작이 아니다”라고 느끼게 하는 장치

## 11.1 화면에 반드시 노출할 것

- `requestId`
- `correlationId`
- `사용자 ID`
- `세션 ID`
- `시각`
- `실행 순서`
- `raw JSON 보기`
- `다운로드`

## 11.2 계산식 공개

각 지표 화면에는 아래를 항상 넣는다.

- 전체 항목 수
- 통과 항목 수
- 실패 항목 수
- 점수 계산식
- 현재 점수
- 기준 점수

## 11.3 원본과 계산 결과 분리

화면을 아래 두 칼럼으로 분리한다.

- 왼쪽: `서버가 실제로 기록한 값`
- 오른쪽: `이 값으로 계산한 결과`

이 구분이 없으면 심사위원은 계산값을 가공값으로 의심한다.

## 11.4 준비 실행 공개

특히 `CoR`, `RAP`는 반드시 준비 실행을 공개해야 한다.

숨기면 안 되는 것:

- 다른 사용자 적재 여부
- 잘못된 목적 문서 적재 여부
- 현재 사용자 본 실행 시작 시점

## 12. 구현 우선순위

## 12.1 1차 구현

가장 먼저 만들어야 하는 화면:

그 다음:

1. `CoR`

## 12.3 3차 구현

마지막:

1. `USNS`
2. `BSR`

이유:

- 행동 흐름 시각화와 회차 비교 UX가 가장 중요함

## 13. 최종 결론

11개 지표 브라우저 시연은 **기존 `security-test` 페이지를 확장하는 방식**이 가장 현실적이다.  
하지만 단순 확장만으로는 부족하고, 아래가 반드시 필요하다.

1. 지표별 전용 상세 화면
2. 준비 실행 / 본 실행 분리
3. 원본 사실 / 계산 결과 분리
4. 런타임 prompt / retrieval / lineage 캡처 추가
5. 회차 누적과 오염 여부를 보여 주는 그래프와 표
6. 비전문가용 한국어 라벨

즉 이번 설계의 핵심은:

- **“점수”를 보여 주는 화면이 아니라**
- **“왜 이 점수가 사실인지”를 심사위원이 직접 따라갈 수 있는 화면**을 만드는 것이다.
