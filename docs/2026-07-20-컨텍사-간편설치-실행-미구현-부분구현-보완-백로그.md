# 컨텍사 필수 간편설치·실행 백로그

## 1. 목표

사용자는 별도 지식이나 복잡한 옵션 없이 다음 네 명령만 사용한다.

```text
contexa init
contexa reset
contexa init --simulate
contexa reset --simulate
```

완료 결과는 새로운 기능이 아니라 기존 네 명령이 쉽고 안전하며 오류 없이 동작하는 상태다.

## 2. 절대 불변 조건

1. 기본 init은 build에 시험 채널의 Contexa starter를 정확히 한 번 추가한다.
2. 기본 init은 호스트 Java source, application 설정, Spring Security, IAM, 인증 주체와 권한을 변경하지 않는다.
3. `@EnableAISecurity`가 없으면 Contexa security filter, provider, chain과 admin security 추가는 0건이다.
4. 공통 기본값은 Contexa 모듈의 `*Properties`와 자동설정이 소유한다.
5. reset은 CLI가 실제 변경했다고 증명한 대상만 복구한다.
6. simulation은 normal 설치와 파일·manifest·backup·port·Docker 자원이 분리된다.
7. CLI는 SQL과 migration을 실행하지 않는다. schema는 OSS 또는 Enterprise runtime이 서버 기동 시 기존 기능으로 복구한다.
8. 현재 시험 채널은 SNAPSHOT을 유지한다.
9. 실패, SKIP, 미실행, source 검색과 mock-only 결과는 PASS가 아니다.
10. 각 Phase 완료판정이 100% 통과하기 전에 다음 Phase로 이동하지 않는다.

## 3. 하지 않는 작업

- 새 사용자 명령·옵션·설치 모드 추가
- `status`, `doctor`, `scan` 기능 확대
- 설치 오류와 무관한 리팩터링·클래스 분리·새 모듈 생성
- 신규 Enterprise 기능, schema 기능 또는 inventory 기능 개발
- 줄 수·파일 수를 목표로 한 변경
- H2를 PostgreSQL 완료 근거로 사용
- 사용자 application 설정에 공통 기본값 추가
- `@Lazy`, `ObjectProvider`, bean overriding, 오류 무시로 문제 은폐

## 4. Phase 0 — 사용자 계약과 호스트 비간섭

### ESB-001 네 핵심 명령 계약

구현:

- README, installer 완료 안내와 CLI help가 같은 네 명령을 안내한다.
- 일반 사용자 경로에서 `--yes`, `--force`, `--no-docker`를 숨은 필수조건으로 사용하지 않는다.
- starter가 없을 때 `init --simulate`는 write 0건으로 실패하고 `contexa init`만 안내한다.
- normal 설치가 있으면 `init --simulate`가 조기 종료하지 않는다.

완료판정:

- 네 명령을 표시된 그대로 실제 child process로 실행한다.
- 성공·실패·재실행 exit code와 변경 파일이 계약과 일치한다.
- 숨은 필수 flag와 동작 없는 공개 옵션이 0건이다.

### ESB-002 dependency-only 호스트 비간섭

구현:

- starter-only runtime classpath가 호스트 Spring Security를 새로 유입하지 않는다.
- 명시적 활성화 전 Contexa security bean을 생성하지 않는다.
- 기존 호스트 security chain과 `SecurityContext`를 그대로 보존한다.

완료판정:

- starter 부재와 starter-only의 security bean graph가 동일하다.
- Contexa filter, provider, chain 추가가 0건이다.
- 호스트 login·public·protected endpoint와 principal·authorities·authenticated 상태가 전후 동일하다.

### ESB-003 시험 채널 단일 계약

구현:

- signed channel manifest 하나가 release tag, CLI version, starter SNAPSHOT version, source commit과 asset digest를 소유한다.
- installer는 GitHub `latest`에 의존하지 않고 signed snapshot channel을 사용한다.
- version·signature·digest가 다르면 기존 binary를 변경하기 전에 실패한다.

완료판정:

- 공개 installer로 설치한 binary version·hash와 주입 starter version이 manifest와 일치한다.
- 변조 manifest·signature·asset·version은 모두 non-zero이며 기존 binary digest가 보존된다.

### Phase 0 출구조건

- ESB-001~003 모두 PASS
- 호스트 source·설정·IAM 변경 0건
- 실패·SKIP·미실행 0건

## 5. Phase 1 — 공개 installer

### ESB-004 안전한 설치 수명주기

구현:

- `/install.sh`와 `/install.ps1`이 올바른 UTF-8 script를 반환한다.
- metadata·manifest·signature·binary 요청에 제한된 timeout과 retry를 적용한다.
- 임시 경로에서 signature, digest, architecture, version과 help를 검증한 뒤 원자 교체한다.
- 중단·smoke 실패 시 기존 정상 binary를 복구한다.
- 동일 버전은 no-op이며 PATH 충돌을 성공으로 숨기지 않는다.
- uninstall은 CLI binary와 CLI 소유 PATH만 대상으로 하고 project reset과 구분한다.

완료판정:

- 실제 공개 URL의 status·headers·body SHA-256이 배포 source와 일치한다.
- 신규 설치, no-op, update, rollback, uninstall, PATH 충돌, 404, 429, 5xx, hang, bad signature, bad checksum과 smoke 실패가 통과한다.
- 실패 후 기존 version·digest·PATH가 동일하다.

### ESB-005 installer 3 OS

완료판정:

- Linux x64, macOS ARM64, Windows x64 실제 release asset을 설치한다.
- PowerShell 5.1·7과 POSIX에서 ESB-004를 실행한다.
- 세 OS 모두 설치 직후 `contexa --version`, 기본 init과 reset이 성공한다.

### Phase 1 출구조건

- ESB-004~005 모두 PASS
- 공개 URL과 실제 release asset 사용
- 임시파일·프로세스·설치 잔존물 0건

## 6. Phase 2 — init·reset·simulation

### ESB-006 기본 init 최소 변경

구현:

- Maven, Gradle Groovy·Kotlin과 multi-module에서 Spring Boot owner 하나를 결정한다.
- owner가 없거나 둘 이상이면 write 0건으로 실패한다.
- build와 ownership manifest 외 사용자 프로젝트 파일을 변경하지 않는다.
- application 설정, Java, Docker, GeoIP와 AI provider dependency를 추가하지 않는다.
- repeated init은 안전한 no-op이다.

완료판정:

- 지원 fixture의 올바른 module에 starter를 정확히 한 번 추가하고 compile한다.
- `D:\contexa-started`의 사용자 파일 digest와 호스트 security 결과가 init 전후 동일하다.
- PostgreSQL과 9080에서 compile·기동·HTTP가 성공한다.

### ESB-007 normal reset 안전성

구현:

- CLI가 실제 적용한 build 변경만 원본 byte로 복구한다.
- init 이후 사용자 변경은 보존하거나 conflict로 중단한다.
- manifest·backup이 없거나 손상됐으면 광범위한 삭제 없이 fail-closed한다.
- repeated reset은 명시적 no-op이다.

완료판정:

- init 전과 reset 후 사용자 기준 파일 SHA-256과 Git 상태가 동일하다.
- 사용자 변경, backup 누락, 손상 manifest, 중단 복구가 통과한다.
- DB와 Docker의 무관 자원 변경이 0건이다.

### ESB-008 simulation 격리

구현:

- simulation 전용 overlay, manifest, backup, infra root, port와 Docker project를 사용한다.
- host application 설정과 normal manifest를 변경하지 않는다.
- 점유 port 또는 소유권 불명 자원은 write 전에 실패한다.
- `reset --simulate`는 simulation 소유 자원만 제거한다.

완료판정:

- `init → init --simulate → reset --simulate → reset`과 반대 순서를 우회 flag 없이 실행한다.
- 각 단계에서 상대 mode와 사용자 파일 digest 변화가 0건이다.
- 실제 PostgreSQL·Redis·Kafka·Zookeeper·Ollama health와 protocol을 확인한다.
- container·volume·network 잔존물이 0건이다.

### Phase 2 출구조건

- ESB-006~008 모두 PASS
- 공개 installer가 설치한 실제 binary 사용
- `D:\contexa-started`, PostgreSQL, 9080과 실제 Docker 검증

## 7. Phase 3 — 최종 release 검증

### ESB-009 실제 사용자 흐름

완료판정:

- source 실행이 아니라 공개 installer가 설치한 SEA binary를 사용한다.
- clean, normal, simulation, both, user-modified와 failure-recovery 상태에서 네 명령을 실행한다.
- CLI init/reset 직후 DB schema 변경은 0건이다.
- OSS와 Enterprise server는 기존 runtime 기능으로 자기 schema를 복구한다.
- PostgreSQL·9080 health와 대표 HTTP endpoint가 성공한다.
- bean cycle, NoClassDefFoundError, missing property, 404 route와 connection 오류가 0건이다.

### ESB-010 최종 3 OS gate

완료판정:

- 동일 signed manifest·source commit의 Linux, macOS, Windows binary를 검증한다.
- 각 OS에서 설치와 기본 init/reset을 실행한다.
- Linux 실제 Docker에서 네 명령 전체 상태전이를 실행한다.
- 변경 관련 대상 테스트를 먼저 수행하고 전체 regression은 최종 release 직전에 한 번만 실행한다.
- process, container, volume, fixture, 임시파일과 의도하지 않은 Git 변경이 0건이다.

### Phase 3 출구조건

- ESB-009~010 모두 PASS
- `D:\contexa-started` 실제 사용자 흐름 PASS
- PostgreSQL·9080·HTTP·3 OS PASS
- 미구현 0건, 부분구현 0건, SKIP 0건

```text
ESSENTIAL_INSTALL_EXECUTION_COMPLETE =
    ESB-001..ESB-010 전부 PASS
    AND 미구현 0건
    AND 부분구현 0건
    AND SKIP·미실행 0건
    AND 호스트 IAM·설정·source 회귀 0건
    AND 소유권 없는 삭제 0건
```
