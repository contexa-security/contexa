## 2. 판정 원칙

### 2.1 상태 정의

- `부분구현`: 요구사항 중 일부만 코드로 구현됐거나 실제 사용자 명령과 다른 우회 옵션으로만 검증된 상태
- `세부 미구현`: 해당 세부조건을 수행하는 실행 경로, 복구 경로 또는 검증 경로가 없는 상태
- `완료`: 구현, 대상 테스트, 필요한 실제 서버·DB·HTTP 검증이 모두 통과한 상태

### 2.2 완료 처리 금지

다음 상태에서는 완료로 처리하지 않는다.

- `--yes`, `--force`, `--no-docker` 등 완료판정에 없는 우회 옵션을 추가해야만 핵심 명령이 성공하는 경우
- source 문자열 존재 검사만 통과하고 실제 child process를 실행하지 않은 경우
- mock 테스트만 있고 실제 설치 binary, PostgreSQL, Docker 또는 9080 서버 검증이 필요한 경우
- 테스트가 검증 대상 분기를 실행하지 않고 조기 반환하는 경우
- 이전 release binary와 현재 working tree 구현의 동일성을 증명하지 못한 경우
- CLI와 installer에 존재하지 않는 HTML·JS UI를 검증했다고 보고하는 경우
- 실패 실행, timeout 실행, 부분 복구 실행을 PASS 증거에 포함한 경우

### 2.3 공통 구현 원칙

- `contexa init`, `contexa reset`, `contexa init --simulate`, `contexa reset --simulate`를 일반 사용자의 네 핵심 명령으로 유지한다.
- 새로운 사용자 기능이나 불필요한 옵션을 추가하지 않는다.
- 사용자 프로젝트의 기존 IAM, SecurityContext, 설정, dependency, source를 소유권 근거 없이 변경하지 않는다.
- CLI는 SQL·migration을 실행하지 않는다.
- runtime schema는 OSS runtime과 Enterprise runtime이 각각 자신의 모듈 경계에서 복구한다.
- 하드코딩, 임시 예외 무시, bean overriding, `@Lazy`, `ObjectProvider`로 문제를 숨기지 않는다.
- 기존 정상 기능을 변경할 때는 변경 전후의 공개 명령, 파일 digest, exit code를 회귀 검증한다.
- 각 Phase에서는 해당 Phase 변경과 직접 관련된 대상 테스트만 먼저 실행한다. 전체 release regression은 Phase 6 최종 gate에서 한 번 수행한다.

## 4. Phase 0 — 제품 계약과 소유권 보완

### SIRB-P0-001 네 핵심 명령의 실제 실행 계약 정상화

- 원본 대응: `SIBL-001` / `SIAC-001`
- 현재 분류: 부분구현
- 현재 결함:
  - `contexa init --simulate`는 starter가 없으면 중단한다.
  - starter가 있으면 `--yes` 또는 `--force`가 없을 때 `already detected` 분기로 조기 반환한다.
  - 상태전이 테스트는 항상 `--yes --no-docker`를 추가해 기본 명령 분기를 검증하지 않는다.
  - README의 질문·변경 범위가 실제 구현과 다르다.
- 세부 미구현:
  - 옵션 추가 없는 `contexa init --simulate`의 정상 실행 경로
  - 네 핵심 명령 그대로 실행하는 command-level acceptance test
- 구현 작업:
  1. normal starter 또는 사용자 소유 starter가 존재하면 `init --simulate`가 추가 flag 없이 simulation plan으로 진입하게 한다.
  2. starter가 없으면 파일을 변경하지 않고 `contexa init`을 먼저 수행해야 한다는 안정된 오류 코드와 한 개의 다음 명령을 제공한다.
  3. normal install의 idempotent 조기 반환과 simulation 준비 분기를 분리한다.
  4. installer 완료 안내, CLI help, CLI README의 질문 수·파일 변경 범위·다음 명령을 실제 코드와 일치시킨다.
  5. 일반 사용 경로에서 `--yes`, `--force`, `--no-docker`를 필수 조건으로 만들지 않는다.
- 완료판정:
  - 일반 init 완료 프로젝트에서 `contexa init --simulate`만 실행해 simulation plan과 설치가 진행된다.
  - starter 미존재 프로젝트에서는 write 0건, 안정 오류 코드, `contexa init` 안내가 출력된다.
  - 네 핵심 명령의 성공·실패·재실행 테스트가 실제 child process로 통과한다.
  - README와 실제 plan의 변경 파일 목록이 일치한다.

### SIRB-P0-002 시험 snapshot 채널과 버전 계약 단일화

- 현재 결함:
  - CLI와 release manifest는 `0.1.2-phase6.3`이지만 install-ctxa package와 README에 다른 phase 버전이 남아 있다.
  - installer 기본 lookup은 GitHub `releases/latest`이고 phase tag는 prerelease로 발행된다.
  - 현재 snapshot channel을 아무 옵션 없는 installer와 연결하는 canonical resolver가 없다.
- 세부 미구현:
  - 서명된 channel manifest 또는 동등한 snapshot channel resolver

- 구현 작업:
  1. release manifest 또는 별도 서명 channel manifest 중 하나만 channel, release tag, CLI version, starter version, asset 계약의 canonical source로 정한다.
  2. 기본 installer가 현재 시험 snapshot channel을 해석하도록 하고 GitHub `latest`의 의미에 암묵적으로 의존하지 않게 한다.
  3. install-ctxa의 package version이 installer 자체 버전이라면 CLI 버전과 명확히 분리하고, CLI 버전처럼 사용되는 문서 literal을 제거한다.
  4. README 고정 버전 예시는 canonical manifest에서 생성하거나 검증한다.
  5. installer 표시, 설치 binary `--version`, 주입 starter version이 manifest와 다르면 설치 전에 실패한다.
- 완료판정:
  - 옵션 없는 installer가 현재 시험 channel의 서명된 release를 선택한다.
  - tag, CLI, starter, asset 중 하나를 변경한 fault fixture가 최종 경로 변경 전에 실패한다.

### SIRB-P0-003 normal·simulation 소유권 식별자와 경로 경계 완성

- 원본 대응: `SIBL-004` / `SIAC-004`
- 현재 분류: 부분구현
- 현재 결함:
  - normal과 simulation manifest·backup은 분리됐지만 소유권 metadata에 전체 resource digest가 없다.
  - `--infra-dir`는 단순 `path.resolve()`만 수행하고 허용 root를 검사하지 않는다.
- 세부 미구현:
  - versioned resource digest
  - project root 또는 허용된 Contexa home allowlist
- 구현 작업:
  1. installation ID, canonical project path, mode, CLI version, createdAt, resource digest를 manifest schema에 포함한다.
  2. resource digest는 정렬된 파일 resource ID, infra root, Docker contract로부터 결정적으로 계산한다.
  3. 외부 infra 경로는 허용된 Contexa home 또는 명시적으로 승인된 안전 root인지 realpath 기준으로 검증한다.
  4. project 밖 경로, parent symlink escape, UNC/drive 변경, `..`를 write 전에 거부한다.
  5. manifest version migration은 소유권을 증명할 수 있는 경우에만 수행하고 추정 migration을 금지한다.
- 완료판정:
  - normal/simulation manifest가 서로 다른 installation ID와 resource digest를 가진다.
  - path escape·symlink·다른 drive fixture에서 write 0건으로 실패한다.
  - status가 두 mode와 digest conflict를 구분한다.

### SIRB-P0-004 plan·transaction·중단 복구 완성

- 원본 대응: `SIBL-005` / `SIAC-005`
- 현재 분류: 부분구현
- 현재 결함:
  - 파일 rollback은 구현됐지만 plan에 manifest write와 모든 외부 작업이 완전히 표현되지 않는다.
  - Docker 시작 후 강제 종료된 transaction을 다음 실행에서 정리할 영속 lifecycle 상태가 없다.
  - commit 후 외부 compose의 이전 상태를 reset에서 복구할 계약이 부족하다.
- 세부 미구현:
  - 파일·외부 artifact·Docker를 포함하는 영속 transaction journal
- 구현 작업:
  1. plan에 create/modify/delete/download/Docker start·reuse·remove/manifest commit을 모두 기록한다.
  2. 각 단계에 `PLANNED`, `PREPARED`, `APPLIED`, `COMMITTED`, `ROLLBACK_FAILED` 상태를 영속 기록한다.
  3. Docker start 전 exact resource contract와 cleanup action을 journal에 기록한다.
  4. 다음 init은 미완료 transaction을 감지하고 파일과 Docker를 역순 복구한 뒤에만 새 plan을 시작한다.
  5. 기존 외부 compose를 허용한다면 reset용 원본 snapshot을 commit 후에도 보존하고, 허용하지 않는다면 write 전에 명확히 거부한다.
- 완료판정:
  - 모든 mutation 단계와 Docker start 직후 process-kill fault에서 다음 init이 사전 digest와 자원 상태를 복구한다.
  - rollback 실패 시 성공 문구가 없고 manifest·backup·journal이 보존된다.

## 5. Phase 1 — install-ctxa 보완

### SIRB-P1-001 bounded latest resolution 완성

- 원본 대응: `SIBL-007` / `SIAC-007`
- 현재 분류: 부분구현
- 현재 결함:
  - HTTP timeout과 제한 retry는 구현됐다.
  - 기본 channel resolution은 GitHub release API에 직접 의존하며 rate-limit 또는 prerelease channel 차이를 독립적으로 해결하지 못한다.
- 세부 미구현:
  - 서명된 channel metadata 기반 latest resolution
- 구현 작업:
  1. SIRB-P0-002의 channel manifest를 installer의 기본 resolution 경로로 사용한다.
  2. metadata, manifest, signature, checksum, binary 요청에 connect·total timeout과 제한 retry를 공통 적용한다.
  3. 429·rate-limit·5xx·connection reset을 구분하고 재시도 가능 여부와 다음 조치를 출력한다.
  4. 모든 요청은 정해진 상한시간 안에 종료한다.
- 완료판정:
  - fake 429, 5xx, connection reset, hang server에서 상한시간·retry 횟수·non-zero exit가 일치한다.
  - 기존 CLI binary digest는 모든 실패 전후 동일하다.

### SIRB-P1-002 installer 강제 중단 복구

- 원본 대응: `SIBL-009` / `SIAC-009`
- 현재 분류: 부분구현
- 현재 결함:
  - 일반 move/smoke 오류 rollback은 구현됐다.
  - 기존 binary를 `.previous`로 이동한 직후 프로세스가 강제 종료되면 기본 명령 경로가 일시적으로 사라질 수 있다.
- 세부 미구현:
  - installer 교체 journal과 다음 실행 자동 복구
- 구현 작업:
  1. 최종 경로와 같은 파일시스템에 installer transaction marker를 기록한다.
  2. `DOWNLOADED`, `VERIFIED`, `OLD_MOVED`, `NEW_MOVED`, `SMOKE_PASSED` 상태를 기록한다.
  3. installer 시작 시 미완료 marker를 먼저 복구하고 old/new binary를 각각 smoke한다.
  4. 양쪽 중 정상 binary 하나를 최종 경로로 원자 복구하고 모호한 상태에서는 임의 삭제하지 않는다.
  5. 성공 후 marker와 임시파일만 제거하고 rollback용 `.previous` 정책은 유지한다.
- 완료판정:
  - 각 교체 상태에서 process-kill 후 재실행했을 때 정상 old 또는 new binary가 `contexa`로 실행된다.
  - 사용자 소유 legacy binary를 삭제하지 않는다.

### SIRB-P1-003 installer 교차 플랫폼 fault matrix 완성

- 원본 대응: `SIBL-015` / `SIAC-015`
- 현재 분류: 부분구현
- 현재 결함:
  - PowerShell fault matrix는 존재한다.
  - POSIX installer에서 404, timeout, signature mismatch, checksum mismatch, smoke rollback 전체 행렬이 동등하게 검증되지 않는다.
  - install-ctxa와 contexa-cli release contract가 동일 CI gate에서 항상 실행되지 않는다.
- 세부 미구현:
  - POSIX 전체 failure/rollback 실행 테스트
  - 두 저장소의 단일 release contract gate
- 구현 작업:
  1. 동일 fake release server fixture를 PowerShell과 POSIX가 공유한다.
  2. 신규 설치, no-op, update, rollback, uninstall, 404, hang, bad signature, bad checksum, bad architecture, final smoke failure를 두 installer에서 실행한다.
  3. CLI release workflow가 생성한 asset 이름·manifest·signature를 install-ctxa acceptance job이 직접 소비하게 한다.
  4. installer source 문자열 검사만으로 fault test를 대체하지 않는다.
- 완료판정:
  - Windows PowerShell 5.1/7, Linux POSIX, macOS POSIX에서 해당 matrix가 모두 통과한다.
  - 실패 후 기존 binary와 PATH가 보존된다.

### SIRB-P2-001 Spring Boot build 구조 판정 강화

  - 네 핵심 명령 원형 그대로의 pseudo-terminal·Docker 상태전이
- 구현 작업:
  1. interactive 입력은 pseudo-terminal에서 Enter·필수 동의만 전달한다.
  2. 명령 문자열은 네 핵심 명령과 `--dir` 같은 fixture 위치 지정 외 우회 flag를 사용하지 않는다.
  3. clean, normal, simulation, both, user-modified, failed-recovery 상태를 실행한다.
  4. exit code, stdout/stderr token, file digest, manifest, Docker label·volume을 단계마다 기록한다.
- 완료판정:
  - 필수 순서 전체가 실제 child process와 실제 Docker로 통과한다.
  - normal reset과 simulation reset의 상대 상태 변경이 0건이다.

### SIRB-P6-002 release source·installer·runtime 단일 최종 gate

- 원본 대응: `SIBL-045` / `SIAC-045`
- 현재 분류: 부분구현
- 현재 결함:
  - CLI와 install-ctxa workflow가 분리되어 동일 산출물을 하나의 gate에서 항상 검증하지 않는다.
  - 현재 contexa-cli working tree에 미커밋 변경이 있어 기존 release asset과 현재 source 동일성이 증명되지 않는다.
  - phase release 조건에 따라 전체 기존 regression이 실행되지 않는 경우가 있다.
- 세부 미구현:
  - commit SHA·manifest·binary digest·installer 결과를 연결하는 provenance gate
  - 현재 구현으로 생성된 실제 release asset의 최종 검증
- 구현 작업:
  1. source commit SHA를 signed release manifest에 기록한다.
  2. CLI workflow가 생성한 exact asset을 installer workflow에 전달한다.
  3. installer가 설치한 binary hash와 manifest asset hash를 비교한다.
  4. 해당 binary로 네 핵심 명령, 9080 server, PostgreSQL 검증을 수행한다.
  5. 변경 관련 대상 테스트를 먼저 수행하고 최종 release 직전에 기존 regression 전체를 한 번 수행한다.

  - Linux x64, macOS ARM64, Windows x64에서 동일 signed manifest provenance가 확인된다.
  - 신규 설치, no-op, update, rollback, PATH conflict, signature/checksum/smoke failure가 통과한다.
  - 테스트 후 프로세스·container·volume·fixture 변경 잔존 0건이다.

## 11. Phase 7 — preflight identity 보완

### SIRB-P7-001 모든 점유 포트의 서비스 identity 검증

- 원본 대응: `SIBL-054` / `SIAC-054`
- 현재 분류: 완료
- 해결 전 결함:
  - exact Docker owner·mode·project·installation label 검증은 구현됐다.
  - PostgreSQL/Redis/Kafka protocol 검증은 expected-name owned container에만 수행된다.
  - 외부 프로세스가 포트를 점유하면 실제 protocol identity 없이 `unverified-port-in-use`로만 처리한다.
- 세부 미구현:
  - 모든 점유 포트에 대한 bounded host-level protocol probe
- 구현 작업:
  1. port bound와 service identity 상태를 별도 결과로 모델링한다.
  2. PostgreSQL은 protocol, database, user를 제한 시간 내 확인한다.
  3. Redis는 RESP PING과 필요한 비민감 server fingerprint를 확인한다.
  4. Kafka는 broker handshake와 cluster ID를 확인한다.
  5. Zookeeper·Ollama는 해당 mode에서 요구될 때 protocol/version을 확인한다.
  6. 기대 identity가 아니거나 인증 없이 확인할 수 없으면 write와 Docker up 전에 실패한다.
  7. password·token은 로그와 manifest에 기록하지 않고 비민감 hash만 저장한다.
- 완료판정:
  - foreign PostgreSQL, wrong database/user, Redis decoy, Kafka decoy, HTTP decoy, silent socket fixture가 모두 제한 시간 내 pre-write non-zero로 실패한다.
  - 동일 owner의 정확한 서비스만 재사용한다.
- 구현·검증 결과:
  - 모든 점유 포트에서 bounded host protocol probe를 실행한다.
  - Redis version, Kafka cluster ID, Zookeeper/Ollama version, PostgreSQL database/user 계약을 fail-closed로 검증한다.
  - 대상 테스트 16/16과 실제 CLI decoy pre-write 실패가 통과했다.
  - project digest·Docker inventory·PostgreSQL schema inventory 변경은 모두 0건이다.
