## 1. 충실도 원칙 (이 계획의 최상위 규칙)

1. **1:1 추적**: 화면 설계서의 모든 화면·부품·문구·값·작업·검수 기준을 추적표(11절)의 행으로 만든다. 행마다 다음을 적는다.
   - 설계서 출처(슬라이드 id 또는 글 정본 절)
   - 구현 위치
   - 검수 ID
   - 증거
2. **빼지 않고, 줄이지 않고, 바꾸지 않는다**: 구현 중 설계와 달라져야 하면 먼저 추적표에 '변경'과 사유를 적는다. 그 자리에서 사용자에게 알리고 승인을 받은 뒤 진행한다.
3. **순서와 관문**: 단계(5절)는 순서대로 한다. 앞 단계의 검수가 모두 PASS이고, 실서버 확인이 있고, 사용자 승인이 있어야 다음 단계를 시작한다.
4. **신뢰 원칙 구현 규칙** (설계서 1절, trust·source 장)
   - 화면은 계산하지 않는다. 화면의 모든 숫자·판정·근거 문장은 API 응답 값이다.
   - 비율과 집계는 포털(측정 기록)이 계산하고 계산식을 함께 내려준다.
   - 웹 코드에 측정 숫자 상수를 두지 않는다. 무결성 검사로 강제한다.
   - 모든 값 옆에 출처 표식을 둔다. 출처는 엔진 판정 기록·업무 DB·사례 정의·측정 기록 넷 중 하나이며, 실행 번호와 기록 시각(세계 표준시)을 함께 보인다.
   - 쉬운 말 옆에 원문을 둔다. 실행 기록은 내려받을 수 있고 SHA-256을 함께 보인다.
   - 번역 원칙: 고정 라벨과 시스템이 정한 근거 문장은 고정 한국어 대응을 쓴다. 모델이 자유롭게 쓴 문장은 원문과 '번역' 표시를 함께 둔다. 기본 화면에서 무엇을 먼저 보일지는 영어 노출 0 기준과 충돌하므로 D-29(결정 7과 함께)로 정한다.
5. **지어낸 값 금지**: 설계서의 예시 값(run-d9e438853e46 등)은 '그 실행 기록을 불러오면 같은 값이 나와야 한다'는 검수 기준으로만 쓴다. 화면에 박지 않는다. Contexa가 틀린 실행이면 문장도 그대로 쓴다.
6. **문구 원천**: 슬라이드 legend 장 노트대로 와이어 안의 글은 '실제로 쓸 문구 초안'이다. 화면의 머리글·주 버튼·보조 링크·'방금 본 것' 문장·예고 카드 문구는 7.0 문구 원천표와 슬라이드 와이어에서 그대로 옮긴다. 와이어가 측정 숫자를 담은 문장은 '틀 + 서버 값'으로 바꾼다(8절). S0에서 와이어 전체 글을 i18n 초안으로 뽑아 키와 슬라이드 id를 대응시킨다.
7. **숫자 표기**: 초는 밀리초를 소수 첫째 자리로 반올림해 한 가지로만 쓴다(예: 7,964ms → 8.0초). 건수는 천 단위 쉼표. 같은 값은 모든 화면에서 같은 표기다. 측정 값(예고 카드, 측정 집계)과 방문자 실행 값(체험 화면)은 출처 표식에서 '측정'·'이번 실행'으로 구분한다. 예고 숫자와 다음 화면 값이 다를 수 있으므로, 예고 카드에는 '측정' 표시를 붙인다.
8. **코어 불변**: 코어는 공용이다. 데모 때문에 바꾸지 않는다. 공용 관점의 결함이면 별도 승인을 받고 수정 전·후를 실서버로 확인한다(구현 전 작업 12, Q-47).
9. **코드 규칙**
   - 주석·로그는 영어로 쓰고, 로그는 error만 남긴다. FQCN·이모지는 쓰지 않는다.
   - 파일의 줄바꿈 형식을 유지하고 `checkJavaStyle`을 통과한다.
   - 하드코딩 대체, 실제 흐름 우회, 데이터 날조는 금지한다.
   - 테스트는 바꾼 부분과 관련된 것만 돌린다. 전체 테스트는 지시가 있을 때만 돌린다.
   - 커밋은 사용자가 한다.
   - 비밀값(`showcase.env`, 내부 서명 키, `docs/APIKEY.md`)은 열거나 출력하거나 스테이징하지 않는다.
   - 사용자 컨테이너(contexa-lab-*, contexa-runtime-lab-*, contexa-postgres, contexa-redis)와 포트 5432·6379는 건드리지 않는다. 삭제는 사용자에게 목록으로 요청한다.

## 3. 정확성 주의 사항 (설계서 문구를 구현할 때 틀리기 쉬운 사실)

- **본인 확인 통과와 학습** (learn-after, e2-check, Q-46): 학습되는 것은 '확인 성공' 한 건이다. 행동 기록 25→26건이며, 기록 시각은 회사 시각이 아니라 서버 시각이다. 확인 뒤 다시 보낸 원래 요청은 재분석·학습되지 않는다(`reissue_reanalysed=false`). 화면은 둘을 구분해 쓴다.
- **훅의 진짜 직원 칸**: 3회 중 1회는 본인 확인 뒤 통과였다. 칸 아래에 그대로 적는다.
  - 재생은 대표 실행 한 건(run-655307ba26be)이다. 아래 한 줄은 같은 측정의 3회 집계(서버 값)다.
- **허용 근거가 승인을 말하지 않음** (e2-reason, lab-3): 허용 문장은 판단 규칙 3이 정한 문장(PLATFORM_CANONICAL)이다. '규칙이 정한 문장이라 승인을 말하지 않음'을 표시한다.
- **동기식·비동기식 업무 형태**: 결정 3(같은 업무를 두 방식으로 받는 주소)이 구현되기 전에는 '일반 반출(동기식)' 대 '스트리밍 반출(비동기식)'이라고 업무 형태가 다름을 화면에 밝힌다(sync-try, sync-compare 노트).
- **비동기식 본인 확인은 스트림을 멈추지 않는다**: 차단만 전송 도중에 끊는다(CUT). 이 사실을 sync-concept·sync-when에 그대로 쓴다.
- **관측 21에서 시작**: 업무 프로필은 요청 시각 직전 7일만 쓴다(meter, e3-stack). 템플릿 25건과 다른 이유를 출처 표식에 적는다.
- **평소 시각 목록 두 개**: 빈도 상위 6개(NormalAccessHours)와 한 번이라도 나온 시각(ObservedHours)이다. 둘 다 보인다(g-learned, 작업 10).
- **10-05 'limited baseline' 대 10-07 본인 확인** (g-learn-why 노트): 사이에 회사 기록 연동 수정이 있었다. 그래서 본문에 인과로 쓰지 않고, 출처 표식 안에만 사실로 둔다.
- **업무 기록 규칙**: 모든 화면에서 '이 사례의 조건을 보고 미리 써 둔 규칙' 표시(*)와 함께 쓴다. 근거 공지는 C2_WRITTEN_FOR_THE_CASES다.
- **원문 보존 기간** (anat-2 노트): 프롬프트·응답 원문은 포털에 90일 보관하고, D 메모리에는 최근 1,000건만 있다. 훅·프롬프트 들여다보기·'369줄' 예고가 기대는 대표 실행은 원문 보관 기간 안의 측정 실행으로만 지정한다. 기간이 다가오면 운영 현황에 경보를 남기고, 새 측정 실행으로 다시 지정한다(작업 6·17). 대표 실행 원문만 보존 예외로 두는 안은 보존 정책 변경이므로 사용자 승인 대상이다.
- **'더 많이 막는다'를 주장하지 않는다**: 위험 판단 31회는 모두 막았고, 놓친 11회는 판단이 허용이었다. 이 두 사실을 함께 쓴다(identity, value, bench-judge).

공통 부작용: 업무 코드(`RbacPolicy`, `@Protectable`), 사례, 규칙 클래스를 바꾸거나 커밋하면 다음이 바뀐다.
- 규칙 버전 해시(`RuleVersion.DECIDING_CLASSES`)

### 7.6 실험실 (lab-0 ~ lab-rules)

- **L0 입구**
  - 한 문장 목적: "조건 하나를 바꾸면 판정이 달라질까요?"
  - 세 단계: 1 사례 고르기 / 2 조건 하나 바꾸기 / 3 예측하고 보내기, 직전과 비교
  - 영향 범위: 바꾼 조건은 이번 실행에만 쓰인다. 데모 회사의 설정과 다른 방문자의 기록은 바뀌지 않는다.
  - 오늘 남은 실행 [n]회
  - 버튼: '사례 고르기'(주), '규칙을 직접 조여 보기'
- **L1 사례 고르기**
  - 사례 카드: 직원·상황 한 줄 / 정답 칩 / Contexa 최근 [k]/[n] 맞음
  - 필터: 모두·공격·정상 업무
  - 6개씩 보이고 '더 보기'
  - 직원 카드와 학습 그래프는 '평소 모습 보기' 모달로 옮긴다.
- **L2 조건 하나 바꾸기**
  - 원래 사례 요약
  - 바꿀 항목 하나 고르기: 시각·장소·기기·건수·승인 기록. 사례마다 바꿀 수 없는 항목은 감춘다.
  - 고른 항목의 입력 하나
  - '여러 조건 한꺼번에 바꾸기(고급)' 접기 안에 지금의 입력 15개를 둔다.
  - 보조 링크: '[직원]의 평소 모습 보기'(모달)
  - 주 버튼: '다음 · 예측하고 보내기'
- **L2-2 보내기 전 비교** (lab-compare)
  - 세 칸: 평소와 다른 점 3→3 / 회사 기록 걸림 2→0 / 꼭 지키는 선 해당 여부
  - "이 비교로 보면 올바른 판단은 [통과]입니다"
  - 데이터: 보내기 전 비교 조회(작업 8). 없으면 직전 실행을 쓰고 실행 번호를 표시한다. 같은 조건의 실행이 아예 없으면 '보내기 전 비교 기록 없음'을 쓰고 보낸 뒤 해부에서 비교를 보인다.
  - 주 버튼: '예측하고 보내기'
- **L2-3 예측하고 보내기** (lab-0 3단계, lab-2·lab-compare 버튼)
  - 보내기 전에 예측을 고른다: 이 사례가 공격인지 정상 업무인지(모르겠다 포함), 그리고 방식별 예상. 기존 실험실 판단 저장(`visitor_prediction`, `startLabRun`의 prediction)을 쓴다.
  - 사람 확인 토큰(Turnstile)과 오늘 남은 실행 수를 함께 보인다.
  - 실행 중에는 체험과 같은 시간 막대와 들여다보기 패널을 쓰고, 요청이 여러 개인 사례(실험실 연속 보내기)는 누적 계기판을 위쪽에 고정한다(meter).
- **L3 결과와 근거 비교** (lab-3)
  - 결과 문장. 결과가 그대로면 "판정이 바뀌지 않았습니다"와 그 근거를 쓴다.
  - 직전 대 이번 표: 바뀐 칸만 강조
  - 내 예측 대 결과: 예측과 실제 결과·정답을 나란히 보인다(값은 서버)
  - 근거 두 칸: '규칙 지정' 표시
  - 버튼: 다른 조건 바꿔 보기 / 판정 자세히 보기 / 이 판정 평가하기(선택)
- **R 규칙 조여 보기** `/lab/rules` (lab-rules)
  - 안내: "사례는 모두 이 데모의 실제 실행 기록입니다. 서버의 실제 규칙으로 다시 판정합니다."
  - 규칙 탭 둘: 숫자 기준 규칙 / 업무 기록. 숫자 기준 탭은 밤 시간대 [시작]~[끝]시, 건수 상한 [N]건, 오래 안 쓴 계정 검사. 업무 기록 탭은 서버가 공개한 조절 항목(승인·티켓·담당·담당 건수 한도·이력·외부망·거짓 티켓 주장, `RuleSettings`)이다. '규칙 더 보기', '기본값으로'
  - 두 숫자: 막은 공격 [k]/[n], 막힌 정상 업무 [m]/[p]
  - 같은 사례에서 Contexa 기록
  - 바뀐 사례 목록
  - 서버의 실제 규칙 클래스로 다시 판정한다(H-10, `POST /api/rules/evaluate`, 기본값은 `GET /api/rules/cases`). 화면은 계산하지 않는다. `domain/rules.ts` 재계산은 지운다.
- 데이터(실험실 공통): `useLabOptions`, `startLabRun`(`POST /api/lab/runs`), `useRecentLabRuns`, `usePeerAssessments`, `AssessPanel` 재사용

### 7.7 판정 자세히 보기 (anat-1, anat-2)

- 모달이며 자기 주소를 갖는다. 제목 줄: '판정 자세히 보기 · {사례 이름} · 요청 {n}/{m}'과 닫기. 요청이 여러 개면 요청 사이를 옮겨 다닌다.
- 여섯 탭: 요약 · 받은 것 · 판단 과정 · 프롬프트 · 정답 · 원문
  - **요약**: 판정 + 정답 대비 / 사실 3칸 / 판정 시점·초 / 나간 자료 / 학습 a→b / 근거 쉬운 말 / 위험도·확신도(없으면 '값 없음') / 후속
  - **받은 것**: 다른 항목만 강조, 같은 항목 '더 보기', 회사 기록 [n]줄, 과거 기록 [n]건
  - **판단 과정**: 단계와 시간, 모델 호출 수, 2차 분석 여부(1차가 '검토로 넘김'일 때만)
  - **프롬프트**: 체험의 프롬프트 화면과 같은 일곱 묶음
  - **정답**: 정답과 출처(회사 기록), 맞는 대응(차단·본인 확인·검토로 넘김, D-28), 정답 근거 문장(사례 JSON, 작업 3)
  - **원문**: 판단 규칙·상황·응답 JSON·토큰·내려받기(SHA-256)
- 들어오는 곳: 체험 근거, 두 체험 비교, 실험실 결과, 벤치마크 사례, 당신이 한 일
- 9×4 표와 영어 이름표는 첫 탭에서 뺀다.
- 원문 보관 기간이 지나면 '보관 기간이 지나 지웠습니다'를 쓰고 요약 값은 남긴다.
- 데이터: `useAnatomy`, `useExchanges`(원문 탭에서만), 내보내기(SHA-256) 재사용. `DecisionAnatomy`의 섹션을 6탭으로 다시 묶는다
- 수용 기준: W3-시안 대조표(V-11)의 판정 설명 요소 17개가 6탭 어딘가에 모두 남는다. 실시간 단계, 근거 문장, 위험·확신, MITRE, 모델·토큰·지연, 프롬프트 원문, 정답 대비, 장애 표시 등이 여기에 들어간다.

### 7.8 벤치마크 (bench-1 ~ honest, bench-fix)

- **B1 요약** `/benchmark`
  - 범위 한 줄: 날짜·시각, 사례 수, 실행 수, 판정 못 함, 원자료 내려받기
  - 결론 세 칸(질문형): 공격을 가장 많이 막은 것은? / 정상 업무를 가장 많이 막은 것은? / 정상을 막지 않고 공격에 반응한 것은? 답의 방식 이름과 숫자는 서버가 측정에서 고른다(옛 측정: 업무 기록* / 숫자 기준 / 업무 기록* 36·Contexa 34·경계 보안 3·권한 검사 3, D-39)
  - 표 하나: 방식 × 처음부터 다 막음·일부라도 막음·정상 업무를 막지 않음
  - 탭 링크: 사례별로 보기 · 판단과 시점 · 한계 · 측정 방법
  - '이 결과 읽는 법' 접는 상자를 표 바로 옆에 둔다. 내용: 높을수록 좋은 숫자와 낮을수록 좋은 숫자, 실행이 적은 칸의 '예비' 표시, 다섯 방식 모두 같은 사례·같은 시각·같은 데이터.
  - 행을 누르면 방식 카드 모달: 점수 셋, 오차 범위(95%), 틀린 유형별 건수, 이 데모의 설정
- **B1-2 판단과 시점**: 누적 막대 3·9·22·11과 결론 두 줄(시점 → 동기식, 판단 → 한계). 값은 측정 기록 계산(작업 16)이다.
- **B2 사례 목록** `/benchmark/cases`
  - 탭: 공격 사례 [n] / 정상 업무 사례 [m] / 운영 지표
  - 필터 'Contexa가 틀린 사례만 · [k]건'
  - 10행씩 쪽을 나눈다. 제목 숫자는 전체 건수다.
  - 방문자 평가와 운영 지표는 '운영 지표' 탭으로 옮긴다.
- **B3 모달**
  - 사례 모달: 설명, 정답과 출처, 방식별 결과, 최근 실행 → 판정 자세히 보기. 모달 자리를 바꾸고 '뒤로'로 돌아온다.
  - 측정 방법 모달: 계산식(공격을 막은 비율 = 막음 ÷ (공격 실행 − 판정 못 함)), 정답 기준, 오차 범위의 뜻, 측정 환경
  - 방식 카드 모달의 틀린 유형별 건수: 공격을 놓침, 일부 나간 뒤 막음, 정상 업무를 막음, 판정 못 함
  - 모달 안에서 또 모달을 열지 않는다. 사례 모달의 실행을 누르면 판정 자세히 보기가 모달 자리를 바꿔 열리고, '뒤로'로 사례 모달에 돌아온다.
- **휴대폰**: 1층에는 방식 카드만 둔다. 표는 카드로 바꾸고, 사례 목록 행은 사례 카드로 바꾼다(mobile, bench-2).
- **B4 한계** `/benchmark/limits`
  - 세 번 모두 놓친 3가지: S10·S11·S12 카드, 누르면 판정 자세히 보기
  - 큰 숫자 셋: 처음부터 다 막음 · 일부라도 막음 · 판정 전 노출 합계(옛 측정 12/45 · 34/45 · 22,637건, 서버 값)
  - '처음부터 다 막음'이 낮은 이유(22회 시점, 11회 판단)
  - 설명의 한계 두 가지
- **결함 다섯** (bench-fix)
  - 틀린 실행 개수: 20 대 33
  - '일부 나간 뒤 막음' 정의 하나로 통일(결정 6)
  - 정리 버튼 → 실험실
  - 해부에서 돌아오기 → 연 자리
  - 구역 번호 이어짐
  - 숫자 일치 규칙: 같은 원자료, 같은 정의, 제목 = 전체 건수
- 데이터: `useBenchmark(setting)`, `useCases`, 작업 9·13·16의 새 필드. `BenchmarkPage`의 화면 계산(빼기·합)은 서버 필드로 바꾼다

## 8. 숫자가 바뀌어도 거짓이 되지 않게 (문장 틀과 측정 값의 분리)

S1에서 사례(작업 2·3·13)와 업무 주소(작업 1·11)가 바뀌면 측정을 다시 한다. 그러면 설계서의 예시 숫자(15·12, 33·9, 0·31, 3·9·22·11, 21→25 등)가 달라질 수 있다. 다음 규칙으로 구현한다.

1. **문장 틀은 설계서, 이름과 숫자는 측정에서 온다**
   - 예고 카드, 결론 세 칸, 딜레마 결론, 막 끝 카드, 가치 카드의 실측 줄은 '틀 + 서버 값'으로 만든다.
   - 예: "정상 업무 막음 {a}회 대 {b}회".
2. **사실 조건 검사**
   - 틀이 사실을 단정하는 문장이면 서버가 측정 값으로 조건을 검사한다. 대상은 다음과 같다.
     - 훅의 질문 "미리 써 둔 규칙 없이 둘을 구별했습니다"(대표 실행과 3회 집계가 공격은 막고 진짜 직원은 통과일 때만 참)
     - 예고 카드 "숫자 규칙은 막았습니다"
     - 결론 "가장 많이 막은 것은 {방식}"
     - "위험이라고 판단한 공격은 모두 막았습니다"
     - 체험 결과의 "이 공격은 숫자·기록 규칙도 막았습니다"(방문자 실행 기준)
   - 조건이 거짓이면 그 문장을 내리고 사실 문장으로 바꾼다. 예: "숫자 규칙은 이번 측정에서 통과시켰습니다".
   - 대체 문장은 설계 문구를 바꾸는 것이므로, 문장마다 미리 사용자 승인을 받아 사전에 넣는다. 승인되지 않은 대체가 필요해지면 그 카드를 내리고 운영 현황에 경보를 남긴 뒤 승인을 요청한다(작업 19).
3. **대표 실행 지정**
   - 훅·예시 화면의 대표 실행은 운영 API로 지정하고 실행 번호를 화면에 표시한다.
   - 3회 집계 줄은 같은 측정 전체에서 서버가 센다(작업 17).
4. **측정 바꿈 표시**: 측정 설정이 바뀌면 화면 범위 줄(날짜·사례·실행 수)이 따라 바뀐다. 옛 측정은 설정 선택으로 계속 볼 수 있다(`/api/benchmark?setting=`).

## 12. 웹 구현 구조 (`contexa-showcase/web`, 조사 결과 반영)

### 12.1 지금 상태 (2026-10-08 조사)
- **기술 구성**
  - React 19, TypeScript 6(strict), Vite 8을 쓴다. 개발 서버는 5180이고 `/api`를 포털 19180으로 넘긴다.
  - 라우팅은 react-router-dom 7, 서버 상태는 @tanstack/react-query 5, 다국어는 i18next(ko/en 평평한 JSON 각 797키)다.
  - 스타일은 CSS Modules와 `styles/tokens.css`다. stylelint가 토큰만 쓰도록 강제한다.
  - 운영에서는 포털이 번들을 서빙하고, 딥링크는 `SinglePageApplicationConfiguration`이 받는다.
- **작업 트리**: 아직 커밋하지 않은 W4 변경이 많다(삭제 파일, 새 `pages/show|lab|benchmark`, `components/show|anatomy|approaches|assessment`). S0에서 사용자가 커밋할지 먼저 확인한다.
- **실시간**: SSE·WebSocket은 없고 react-query 폴링이다(250ms·300ms·1s). 분석 신호는 단계·시각·행동·위험도만 주고, 근거는 실행이 끝난 뒤 해부에서만 나온다.
- **장면 상태 결함**
  - `ShowPage`는 장면을 `useState`에만 둔다. 그래서 새로고침하면 처음으로 돌아가고, 뒤로 가기는 데모 밖으로 나간다.
  - 실행 중에 새로고침하면 `attempt`를 잃는다. 서버에 앞 실행이 남아 보내기가 막힌다.
- **화면이 계산하는 곳** (신뢰 원칙 3 위반, 모두 서버로 옮긴다)
  - `domain/rules.ts`·`RulesScene`: 규칙을 다시 구현한다. `POST /api/rules/evaluate`가 있는데도 쓰지 않는다.
  - `domain/show.ts`: `conclusion`·`detailsOf`·`leakedThroughExisting`·`differences`를 계산한다.
  - `AnalysisPanel.goodFor`, `ApproachStrip.toneOf`
  - `BenchmarkPage`: `CardSection`의 빼기·합, `VisitorsSection` 합계, `MatrixValue` 판정
  - `LabPage`: `businessCorrectCount`·`InputDiff`·`outcomeLine`
  - `DecisionAnatomy`: `LearningSection` 차이, `usual.summary` 정규식 추출
  - `EndPage.compareConditions`, `ReplayPage.tally`, `AdoptPage` 판정 합계
- **쉬운 말**: 포털 `ReplayViews.CANONICAL_REASONS`에 정해진 문장 코드 7개가 있다. 그러나 웹은 이 코드를 한국어로 바꾸지 않고, 해부·실시간 응답에는 코드가 실리지 않는다. 엔진 영어 근거가 그대로 노출된다. 규칙 5a 문장은 목록에 없다(작업 4).
- **깨진 자산**
  - `e2e/design.spec.ts`, `e2e/visual/design-visual.spec.ts`와 `visual-baseline/` png 12장: 삭제된 `/design` 대상
  - 루트 `ruleCasesLive.test.ts`: 실행되지 않음
- **쓰지 않는 코드**
  - `AnalysisTimeline`, `OutcomeStrip`, `Stepper`
  - 훅 `useLiveResult`, `usePairs`
  - 의존성 `framer-motion`
- **모바일 e2e**: 포털 e2e의 모바일 폭은 360이다. 설계는 390이므로 S11에서 390을 더한다(360은 유지).
- **글꼴**: 새 한국어 문구에 없던 글자가 들어가면 `scripts/font-subset.py`로 부분 글꼴을 다시 만든다. `fontCoverage.test.ts`가 강제한다.
