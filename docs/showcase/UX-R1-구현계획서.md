## 6. 시험 전략

- **단위 · 화면 시험(vitest, 먼저 씀)**: 부품마다 역할 · 상태(기본 · 비활성 · 불러오는 중 · 빈 · 오류) · 접근성 이름, 화면마다 데이터 → 표시 대조(가짜 응답이 아닌 실제 응답 형태의 고정 자료), 경로 넘김 표.
- **실서버 확인(단계마다 한 번)**: 웹 빌드 → 포털 재시작(포털만) → Playwright로 실제 화면을 열고, 실제 실행을 보내 판정까지 진행 → 화면 숫자를 HTTP 응답 · DB 행과 대조.
- **사진 검수**: 단계가 만든 화면을 1440 · 390(마지막 단계는 5폭) × 한 · 영 × 다크 · 라이트로 찍고, 자동 검사(카드 밖 넘침 · 가로 스크롤 · 글자 크기 종류 · 버튼 높이 · 토큰 밖 값)와 눈 검수를 한다.
- **스크롤 상자 안 가려짐(I-5에서 추가, 2026-10-31)**: 자동 검사는 키보드로 갈 수 있는 스크롤 상자 안의 넘침을 "카드 밖 넘침"으로 세지 않는다. I-5에서 표의 열이 이렇게 가려진 것을 사진으로만 찾았다(DEC-47). I-10 전수 검수에서는 `ux_measure.mjs`가 내용이 상자보다 넓은 스크롤 상자를 따로 보고하게 하고, 휴대폰의 수치 표(첫 열 고정 · 옆으로 스크롤, 기획안 설계)를 뺀 나머지를 사진으로 확인한다.
- **화면이 그려지지 않음(I-6에서 추가, 2026-10-31)**: 화면이 예외로 통째로 비면 넘침 · 대비 · 한 글자 줄 검사는 볼 것이 없어 "깨끗"으로 나온다. I-6에서 InjecAgent 사례 보기가 이렇게 비었는데(묶음의 공격 도구가 목록인데 형식 정의는 문자열) 운영 묶음 측정 4차가 문제 0으로 셌다. 그래서 `ux_measure.mjs`는 페이지 오류(`pageerror`)와 h1 없음을 문제로 세고, 끝에 문제 조합 수를 출력한다. 화면 시험은 실제 결과 묶음으로 모든 벤치마크의 모든 탭을 한 번씩 그려 본다(`benchmarks.test.tsx`). 이후 단계의 새 화면도 같은 방식으로 실제 응답 형태로 모든 탭을 그려 본다.
