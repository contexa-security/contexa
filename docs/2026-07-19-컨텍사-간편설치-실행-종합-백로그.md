# 2026-07-19 컨텍사 간편설치·실행 종합 백로그

## 1. 문서 목적

이 문서는 install-ctxa와 contexa-cli를 하나의 설치 제품으로 보고, 사용자가 Contexa 플랫폼을 간단하고 편리하고 쉽게, 그리고 기존 호스트 애플리케이션을 훼손하지 않고 설치·실행·복구할 수 있도록 현재 확인된 문제와 개선 작업을 총괄한다.

이 문서의 목표는 옵션이나 신규 기능을 늘리는 것이 아니다. 사용자가 주로 실행하는 다음 네 명령이 예측 가능하고 안전하며 실제로 동작하도록 만드는 것이 목표다.

    contexa init
    contexa reset
    contexa init --simulate
    contexa reset --simulate

설치 진입점은 다음 두 경로로 한정한다.

    Linux/macOS: install.ctxa.ai/install.sh
    Windows:     install.ctxa.ai/install.ps1

대응 완료판정 문서는 2026-07-19-컨텍사-간편설치-실행-완료판정기준.md 이다. 이 문서의 SIBL-001부터 SIBL-054까지는 완료판정기준의 SIAC-001부터 SIAC-054까지와 1:1로 대응한다.

## 2. 적용 저장소와 책임

| 저장소 | 책임 | 금지 범위 |
| --- | --- | --- |
| install-ctxa | 설치 스크립트 제공, 올바른 CLI 자산 선택, 다운로드 검증, 안전한 설치·업데이트·복구 | 프로젝트 파일 수정, Spring 설정 생성, Docker 인프라 생성 |
| contexa-cli | Spring Boot 프로젝트 탐지, 최소 설치, 설치 소유권 기록, simulation 준비, 정확한 reset | 호스트 IAM 변경, 호스트 SecurityFilterChain 변경, 사용자 소유 설정·의존성 삭제 |
| contexa 모듈 | 기본값, 자동설정, dependency-only 무영향, bridge 이후 독립적인 Zero Trust 실행 | 사용자 application.yml 필수 설정 강제, 레거시 IAM 교체 |
| 사용자 애플리케이션 | 사용자 비즈니스 코드와 기존 인증·인가 유지 | 공통 플랫폼 기본값과 공통 설치 기능 수용 |

contexa-site와 contexa-demo 같은 애플리케이션은 검증용 호스트일 수 있으나, 공통 기능이나 공통 기본값을 추가하는 위치가 아니다. 공통 기본값은 반드시 Contexa 모듈의 Properties와 자동설정이 소유한다.

## 3. 절대 원칙

1. 사용자가 알아야 하는 주 명령은 네 개뿐이어야 한다.
2. 기본 contexa init은 가장 안전한 최소 설치여야 한다.
3. starter-only 또는 dependency-only 상태에서는 호스트 Spring Security와 호스트 IAM에 아무 영향도 주지 않아야 한다.
4. 호스트의 SecurityFilterChain, Authentication, principal, authorities, session, logout, remember-me를 생성·교체·수정하지 않는다.
5. 기존 Spring AI provider 의존성, spring.ai 설정, spring.datasource 설정, spring.security 설정을 삭제하거나 덮어쓰지 않는다.
6. 모든 공통 기본값은 Contexa 모듈의 Properties에 둔다. 사용자가 application.yml을 작성해야만 기동되는 구조를 만들지 않는다.
7. simulation은 일반 설치 및 운영 설정과 파일·manifest·backup·Docker project·port·환경변수 수준에서 분리한다.
8. CLI가 소유권을 증명하지 못하는 파일, 디렉터리, 컨테이너, volume은 삭제하지 않는다.
9. 변경 계획을 출력하고 사전검사를 통과하기 전에 프로젝트 파일을 쓰지 않는다.
10. 성공 메시지는 설치, 검증, 기동 또는 복구가 실제로 성공한 경우에만 출력한다.
11. 부분 성공, 경고 후 진행, 검증 생략을 성공으로 보고하지 않는다.
12. 현재 시험 단계에서 SNAPSHOT 사용은 허용한다. 단, CLI 버전·starter 버전·릴리스 자산 버전은 하나의 시험 채널 manifest에서 관리하며 소스 여러 곳에 분산 하드코딩하지 않는다.
13. 새 기능을 임의로 추가하지 않는다. 기존 설치·실행·reset 계약의 정상화에 필요한 구조 개선만 허용한다.
14. 기존 정상 기능과 사용자 파일을 보존한다. 문자열 치환이나 광범위 삭제를 임시방편으로 사용하지 않는다.
15. 테스트는 변경한 범위부터 실행하고, Phase 완료 시 네 핵심 명령의 교차 상태를 실검증한다.
16. CLI는 데이터베이스 schema를 직접 생성하거나 Enterprise migration을 복제하지 않는다. OSS schema는 contexa-iam runtime이, Enterprise 확장은 Enterprise migration이 소유한다.
17. 전체 table 개수를 301 같은 고정 숫자로 판정하지 않는다. 제품·버전·소유자별 필수 table inventory의 집합 일치로 판정한다.
18. reset이 데이터베이스 volume을 삭제하려면 현재 프로젝트와 CLI 소유권이 모두 증명되어야 하며, 삭제 후 복구는 해당 runtime의 실제 기동으로 검증한다.

## 4. 목표 사용자 계약

### 4.1 install-ctxa

사용자는 한 번의 설치 명령으로 현재 운영체제와 CPU에 맞는 CLI를 설치할 수 있어야 한다. 설치기는 새 바이너리를 기존 바이너리와 교체하기 전에 다운로드 무결성·배포자 신뢰·실행 가능성·버전을 검증해야 한다. 실패하면 기존 정상 바이너리를 유지하거나 자동 복구해야 한다.

### 4.2 contexa init

기본 실행은 Spring Boot 프로젝트를 확인하고 시험 채널이 지정한 starter 의존성을 구조적으로 추가하며 CLI 소유 manifest만 기록한다. 기본값은 Contexa 모듈이 제공한다. Java annotation, Docker, provider 의존성, 호스트 Spring 설정은 명시적 활성화 없이는 변경하지 않는다.

### 4.3 contexa reset

일반 설치 manifest가 소유한 변경만 되돌린다. simulation과 무관한 자원을 건드리지 않는다. 사용자가 변경한 파일은 필드 수준 병합 또는 충돌 보고로 처리하며 파일 전체를 과거 상태로 덮어쓰지 않는다.

### 4.4 contexa init --simulate

일반 설치와 공존하는 별도 simulation profile·manifest·backup·infra를 만든다. 호스트 기본 application.yml을 simulation 값으로 바꾸지 않는다. 운영 환경변수가 이미 있어도 simulation project와 port는 격리된다. 사용자가 복잡한 환경변수를 알지 않아도 실제 애플리케이션을 simulation 인프라에 연결할 수 있는 단일 실행 방법을 제공한다.

### 4.5 contexa reset --simulate

simulation profile, simulation manifest, simulation 소유 인프라만 제거한다. 일반 starter, 일반 설정, 일반 manifest, 사용자 코드와 운영 Docker 자원은 그대로 유지한다.

### 5.1 2026-07-19 실제 설치·실행 검증에서 추가 확인된 결함

| 영역 | 실제 확인 결과 | 필요한 보정 |
| --- | --- | --- |
| 릴리스 버전 | GitHub release는 v0.1.0인데 설치된 `contexa --version`은 1.0.0 | release manifest, 설치기 표시, 설치 바이너리, starter 버전을 단일 계약으로 일치 |
| 첫 실행 UX | 인자 없는 `contexa`가 도움말만 출력하고 exit code 1 반환 | 설치 직후 유효한 첫 실행 경로로 안내와 도움말을 출력하고 정상 종료 |
| 분산 build reset | 분산 의존성 주입 전에 build backup을 만들지 않아 reset 후 의존성 4개가 잔존하고도 성공 처리 | 쓰기 전 backup·checksum과 byte 단위 복구를 강제 |
| manifest 없는 재-reset | 첫 reset이 manifest를 삭제한 뒤 두 번째 reset이 기본 project 이름 `contexa`와 `down -v`를 조합할 수 있음 | manifest 없는 infra reset을 fail-closed로 만들고 반복 reset을 무해하게 처리 |
| OSS 신규 DB | OSS schema 137개 생성 후 공식검사 catalog 12/26 행이 없어 9080 기동 실패 | OSS가 소비하는 catalog seed를 OSS 소유 초기화로 완결 |
| OSS→Enterprise | OSS DB에 Flyway history가 없어 Enterprise가 non-empty schema 오류로 중단 | 검증된 OSS provenance를 기반으로 한 안전한 handoff 제공 |
| Enterprise 신규 DB | Enterprise 153개 migration·299개 table 후 OSS canonical schema가 다시 실행되어 view 의존 DDL 충돌 | 하나의 순서화된 schema coordinator로 base DDL 중복 실행 제거 |
| table 개수 | 운영 301개와 신규 Enterprise 299개의 차이는 host `orders`와 출처 불명 `official_verification_oss_run` | 고정 개수가 아니라 소유자·버전별 inventory와 legacy 분류로 판정 |
| 검증 fixture | `D:\contexa-started`에 JPA 소스는 있으나 JPA dependency가 없어 init 전부터 compile 불가 | 제품 결함과 fixture 선행 결함을 분리하는 clean baseline 고정 |
| preflight | 점유 port의 프로토콜·서비스·Docker 소유자를 검증하지 않고 재사용 가능 | port가 아니라 서비스 identity와 CLI ownership을 검증 |

안전상 실제 실행하지 않은 항목도 결함으로 분류한다. 특히 manifest를 삭제한 뒤 옵션 없이 두 번째 `reset --yes`를 실행하는 경로는 운영 volume 손상 가능성이 있어 정적 경로 분석과 비운영 격리 fixture로만 검증한다.

## 14. Phase 7 — 실제 설치·reset·schema 복구 결함 보정

### SIBL-046 분산 build 변경의 원자적 backup·reset 보장

구현 작업:

- Maven·Gradle 분산 의존성을 쓰기 전에 원본 build 파일 backup과 checksum을 생성하고 manifest에 기록한다.
- build 주입과 manifest 기록을 하나의 transaction에 포함한다.
- reset은 원본 checksum과 backup을 검증한 뒤 byte 단위로 복구한다.
- backup 또는 원본 checksum이 없으면 성공을 보고하거나 manifest를 삭제하지 말고 복구 가능한 상태로 중단한다.

### SIBL-047 manifest 없는 reset의 fail-closed와 반복 안전성

- 프로젝트 이름은 고정 기본값이 아니라 canonical project path와 검증된 manifest의 설치 ID로만 결정한다.
- 첫 reset 뒤 같은 명령을 다시 실행하면 외부 자원을 건드리지 않는 명시적 no-op 또는 안전한 안내로 종료한다.
- Docker `down -v`는 compose 경로, project ID, container label, volume label이 모두 현재 CLI 소유권과 일치할 때만 허용한다.

완료 증거: SIAC-047

### SIBL-048 CLI infra reset과 runtime schema 복구 계약 분리

- reset이 CLI 소유 PostgreSQL volume을 삭제하는 경우 data 소실 사실과 runtime 재기동에 의한 schema 복구 범위를 명확히 보고한다.
- OSS runtime 기동은 OSS schema를, Enterprise runtime 기동은 OSS base와 Enterprise 확장을 정해진 순서로 복구한다.
- host-managed DB와 소유권이 확인되지 않은 volume은 reset 대상에서 제외한다.
- schema 복구와 사용자 data 복구를 구분하고, backup 없는 사용자 data가 복구된다고 표현하지 않는다.

### SIBL-049 OSS 공식검사 catalog seed 소유권 완결

- OSS initializer가 Enterprise migration에만 존재하는 INSERT에 의존하지 않도록 한다.
- 기대 행 수 12/26을 소스의 마법 숫자로만 두지 않고 catalog version·고유 key·checksum 기반 계약으로 관리한다.
- 재기동 시 중복 INSERT 없이 동일 catalog 상태가 유지되도록 한다.

완료 증거: SIAC-049

### SIBL-050 검증된 OSS→Enterprise Flyway handoff

구현 작업:

- Enterprise는 provenance와 실제 필수 object 집합이 모두 일치할 때만 OSS base를 승인하고 Enterprise migration을 이어서 적용한다.
- 출처 불명의 non-empty schema에는 blanket `baseline-on-migrate=true`를 적용하지 않고 안전하게 중단한다.
- OSS base에서 Enterprise로 전환한 DB와 처음부터 Enterprise로 만든 DB가 동일한 Enterprise 소유 schema 결과를 갖게 한다.

- Enterprise migration 이후 OSS canonical `schema.sql`이 다시 실행되지 않도록 초기화 조건과 완료 marker를 통합한다.
- view가 참조하는 column을 뒤늦게 alter하는 등 순서 충돌을 migration dependency로 명시한다.

### SIBL-052 제품·버전·소유자별 schema inventory 도입

구현 작업:

- `orders` 같은 host table과 `official_verification_oss_run` 같은 미소유 object가 제품 완료 수를 왜곡하지 않도록 한다.

완료 증거: SIAC-052

### SIBL-053 D:\contexa-started 실검증 fixture baseline 고정

구현 작업:

- init 전 원본 fixture가 clean compile되는지 먼저 확인하고 source와 build dependency 불일치를 제품 결함과 분리한다.
- fixture 기준 파일의 digest와 Git 상태를 기록한 뒤 실제 설치 바이너리로 init·reset을 실행한다.
- 플랫폼 공통 기능이나 공통 기본값을 fixture에 추가하지 않고 Contexa 모듈의 Properties·자동설정을 사용한다.
- 검증 종료 시 사용자 원본 파일과 Git 상태를 byte 단위로 복구하고 test container·volume·process를 제거한다.

완료 증거: SIAC-053

### SIBL-054 preflight 서비스 identity·소유권 검증

구현 작업:

- port 점유 여부 외에 PostgreSQL protocol·database·user, Redis protocol, Kafka cluster identity를 제한 시간 내 확인한다.
- Docker 서비스는 compose canonical path, project label, service label, installation ID가 모두 일치할 때만 재사용한다.
- 기대 서비스가 아니거나 identity를 확인할 수 없으면 파일 쓰기와 Docker up 전에 실패한다.
- 비밀값을 로그나 manifest에 기록하지 않고 identity 검증에 필요한 비민감 fingerprint만 보존한다.

완료 증거: SIAC-054

## 15. 구현 순서와 Phase 게이트

1. Phase 0이 PASS하기 전에는 installer와 CLI의 소유권·버전 구조를 개별적으로 확장하지 않는다.
2. Phase 1이 PASS하면 설치된 바이너리를 신뢰할 수 있다.
3. Phase 2가 PASS하면 기본 init을 사용자에게 제공할 수 있다.
4. Phase 3이 PASS하면 일반 reset을 제공할 수 있다.
5. Phase 4가 PASS하면 simulation 명령을 제공할 수 있다.
6. Phase 5는 Phase 2~4 구현과 함께 진행할 수 있으나 공개 동작을 변경하는 별도 기능을 만들지 않는다.
7. Phase 6의 실검증과 교차 플랫폼 증거가 모두 PASS해야 전체 완료다.
8. Phase 7은 실제 설치에서 발견된 분산 reset과 schema 복구 결함을 보정하며, OSS 신규 DB·OSS→Enterprise·Enterprise 신규 DB 세 경로가 모두 PASS해야 완료다.

각 Phase에서 미구현, 부분구현, NOT_VERIFIED가 하나라도 발견되면 해당 Phase를 완료 처리하지 않고 같은 Phase의 구현·검증을 반복한다.

## 16. 금지 구현

- @Lazy, ObjectProvider, 광범위 reflection으로 구조 문제를 숨기는 구현
- 기존 사용자 dependency나 설정을 문자열 정규식으로 광범위 삭제하는 구현
- 포트 점유만 보고 외부 서비스를 재사용하는 구현
- 이름이 contexa라는 이유만으로 컨테이너·volume·디렉터리를 삭제하는 구현
- test success 문자열, source grep, mock-only 결과를 실검증으로 보고하는 행위
- Docker·다운로드 실패를 warn으로 삼키고 성공 화면을 출력하는 행위
- 사용자 application.yml에 공통 기본값을 강제로 기록하는 구현
- contexa-site나 contexa-demo에 공통 설치 기능·기본 설정을 추가하는 구현
- H2를 PostgreSQL 완료 근거로 대체하는 행위
- 비밀값, session cookie, API key, DB password 원문을 manifest·로그·증거 문서에 저장하는 행위
- 현재 시험 목적의 SNAPSHOT 사용을 문제로 오인하여 임의로 정식 버전으로 변경하는 행위
- 전체 table 개수 301을 제품 schema 정상성의 고정 기준으로 사용하는 행위
- provenance 확인 없이 non-empty DB에 Flyway baseline을 강제하는 행위
- manifest가 없는 상태에서 기본 project 이름으로 Docker volume을 삭제하는 행위
